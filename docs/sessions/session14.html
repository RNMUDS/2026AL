コードレビューとは

コードレビューとは、他の人が書いたコードを読んで改善点を見つける作業のこと。プロのソフトウェア開発では、ほぼ全てのコードがレビューを経てから本番環境に反映されます。

❓ なぜ「正しさ → 可読性 → 効率性 → 拡張性」の順番？

コードレビューは「動かない最適化されたコード」よりも「動く読みにくいコード」のほうがマシという原則で進めます。具体例で考えてみましょう。

状況レビューで指摘すべきこと
空リストでクラッシュする超高速ソート関数正しさを最優先。速さは後回し。
動くが q, c, n, d ばかりの変数で読めないBFS可読性を改善。意味ある名前へ。
正しくて読みやすいが O(n²) の重複チェック効率性を改善。set でO(n)に。
1関数200行で1つに全部詰まっている拡張性を改善。関数を分割。

💡 まとめ: バグがあるコードは何をしても無意味。まず正しさ、そして読み手のために可読性、最後に性能と拡張性。

例題 1

バグのあるコードを見つける（正しさ）

Python
# --- バグのあるコード ---
def find_max_buggy(numbers):
    """リストの最大値を返す関数（バグあり）"""
    maximum = numbers[0]  # 空リストでエラー！
    for i in range(len(numbers)):
        if numbers[i] > maximum:
            maximum = numbers[i]
    return maximum

# --- 修正版 ---
def find_max_fixed(numbers):
    """リストの最大値を返す関数（修正版）"""
    if not numbers:  # 空リストチェックを追加
        print("警告: 空のリストです")
        return None
    maximum = numbers[0]
    for i in range(1, len(numbers)):  # 2番目から開始
        if numbers[i] > maximum:
            maximum = numbers[i]
    return maximum
  • バグ1: 空リストが渡されると numbers[0] で IndexError（インデックス・エラー）
  • 修正: if not numbers: で空チェックを追加（境界値チェック）
  • 改善: ループを range(1, ...) にして無駄な比較を削除

例題 2

可読性の改善

変数名やコメントを改善して、コードを読みやすくします。例えば、第12回のBFSコードを改善前と改善後で比べると、同じロジックでも読みやすさが大きく変わります。

Python ─ 改善前（読みにくい）
def f(d, s, g):
    q = deque([s])
    v = {s}
    while q:
        c = q.popleft()
        if c == g:
            return True
        for dr, dc in [(-1,0),(1,0),(0,-1),(0,1)]:
            n = (c[0]+dr, c[1]+dc)
            if n not in v:
                v.add(n)
                q.append(n)
    return False
Python ─ 改善後（読みやすい）
def find_shortest_path(maze, start, goal):
    queue = deque([start])
    visited = {start}
    directions = [(-1,0), (1,0), (0,-1), (0,1)]
    while queue:
        current = queue.popleft()
        if current == goal:
            return True
        for dr, dc in directions:
            next_pos = (current[0] + dr, current[1] + dc)
            if next_pos not in visited:
                visited.add(next_pos)
                queue.append(next_pos)
    return False
悪い例良い例理由
f(d, s, g)find_shortest_path(maze, start, goal)関数名・引数名で目的が明確
q, v, p, cqueue, visited, parent, current英語の意味ある単語
n = (x+a, y+b)next_pos = (row+dr, col+dc)何を計算しているか一目で分かる
コメントなし各行にコメント後で読む人（未来の自分）のため

例題 3

効率性の改善（リスト vs セット）

Python
import time

def has_duplicate_slow(data):
    """重複チェック（リスト版 = 遅い O(n^2)）"""
    seen = []  # リストの検索は O(n)
    for item in data:
        if item in seen:  # O(n) の検索が n 回 → O(n^2)
            return True
        seen.append(item)
    return False

def has_duplicate_fast(data):
    """重複チェック（セット版 = 速い O(n)）"""
    seen = set()  # セットの検索は O(1)
    for item in data:
        if item in seen:  # O(1) の検索が n 回 → O(n)
            return True
        seen.add(item)
    return False

エラーハンドリングの追加

Python
def safe_divide(numerator, denominator):
    """安全に割り算をする関数"""
    try:
        result = numerator / denominator
        return result
    except ZeroDivisionError:
        print("  エラー: 0で割ることはできません")
        return None
    except TypeError:
        print("  エラー: 数値でない値が渡されました")
        return None

def validate_maze_input(maze, start, goal):
    """迷路の入力データを検証する関数"""
    errors = []
    if not maze:
        errors.append("迷路が空です")
        return errors
    rows = len(maze)
    cols = len(maze[0])
    sr, sc = start
    if not (0 <= sr < rows and 0 <= sc < cols):
        errors.append(f"スタート{start}が範囲外です")
    elif maze[sr][sc] != 0:
        errors.append(f"スタート{start}が壁です")
    return errors

例題 5

既存コードに機能を追加する

第13回の迷路BFS（幅優先探索）に「探索アニメーション表示」機能を追加します。探索過程で各ステップの隣接マス情報を表示し、BFSの動きを可視化します。

Python
from collections import deque

def bfs_with_trace(maze, start, goal):
    """探索過程を表示するBFS関数"""
    rows = len(maze)
    cols = len(maze[0])
    directions = [(-1, 0), (1, 0), (0, -1), (0, 1)]
    direction_names = ["上", "下", "左", "右"]

    queue = deque([start])  # 探索待ちキュー（deque = デック）
    visited = {start}     # 訪問済みセット
    step = 0

    while queue:
        step += 1
        current = queue.popleft()
        row, col = current

        if current == goal:
            print(f"ステップ{step}: ゴール到達!")
            return True

        # --- 探索過程を表示 ---
        neighbors_info = []
        for i, (dr, dc) in enumerate(directions):
            nr = row + dr
            nc = col + dc
            if not (0 <= nr < rows and 0 <= nc < cols):
                neighbors_info.append(f"{direction_names[i]}:範囲外")
            elif maze[nr][nc] == 1:
                neighbors_info.append(f"{direction_names[i]}:壁")
            elif (nr, nc) in visited:
                neighbors_info.append(f"{direction_names[i]}:訪問済")
            else:
                neighbors_info.append(f"{direction_names[i]}:→{(nr, nc)}")
                visited.add((nr, nc))
                queue.append((nr, nc))

        print(f"ステップ{step}: {current} [{', '.join(neighbors_info)}]")

    return False

例題 例題1 やってみよう 解答

バグ版 find_max_buggy([]) を実行すると、numbers[0] の時点でリストが空のため IndexError が発生する:

Traceback (most recent call last):
  File "AL14-ex1.py", line X, in <module>
    print(find_max_buggy([]))
  File "AL14-ex1.py", line Y, in find_max_buggy
    maximum = numbers[0]
IndexError: list index out of range

一方、修正版 find_max_fixed([]) は if not numbers: で空チェックを行うため、エラーを出さずに警告メッセージを表示して None を返す:

警告: 空のリストです
None

この差が「正しさ」の改善ポイント。境界値（空リスト・0要素・負数など）を想定して事前チェックを入れることで、プログラムは予期せぬクラッシュを避けられる。find_max_fixed([5]) など要素1つのケースでも動作することを併せて確認しておくと安心。

例題 例題2 やってみよう 解答

解答は人によって違うが、典型例として第12回のBFSコードに次のような変数名改善が考えられる:

改善前:
  q = deque()
  q.append(s)
  while q:
      c = q.popleft()
      for d in dirs:
          n = (c[0]+d[0], c[1]+d[1])
          ...

改善後:
  queue = deque()
  queue.append(start)
  while queue:
      current = queue.popleft()
      for dr, dc in directions:
          next_pos = (current[0]+dr, current[1]+dc)
          ...

1文字変数（q, c, n, d）は書くときは速いが、1週間後の自分や他人がコードを読むときに「これは何だっけ？」と止まる原因になる。queue, current, next_pos, directions のように役割が分かる英単語を使うと、コメントなしでも処理の流れが追えるようになる。これが「可読性」の改善。

例題 例題3 やってみよう 解答

data = list(range(5000))（重複なし＝全件探索が最悪ケース）で実行した結果例:

リスト版 has_duplicate_slow: 約 0.30 秒
セット版 has_duplicate_fast: 約 0.0004 秒
速度差: 約 730 倍

環境によって絶対値は変わるが、速度比は数百〜千倍のオーダーになる。理由は計算量の違い: リスト版は item in seen が O(n) なので全体で O(n²)、セット版はハッシュにより O(1) なので全体で O(n)。同じロジックでもデータ構造の選択だけでこれだけの差が出るのが「効率性」の改善ポイント。データが10倍になればリスト版は100倍遅くなり、セット版は10倍にしかならない。

例題 例題4 やってみよう 解答

safe_divide(10, 0) と safe_divide(10, "abc") を実行した結果:

>>> safe_divide(10, 0)
  エラー: 0で割ることはできません
None

>>> safe_divide(10, "abc")
  エラー: 数値でない値が渡されました
None

>>> safe_divide(10, 2)
5.0

try/except で ZeroDivisionError と TypeError を個別にキャッチすることで、エラーごとにユーザーへ分かりやすいメッセージを返せる。プログラムは異常入力でクラッシュせず、None を返して処理を続行する。これが「堅牢性（エラーハンドリング）」の改善。except を1つにまとめない（種類ごとに分ける）ことで、原因を切り分けやすくなる点もポイント。
