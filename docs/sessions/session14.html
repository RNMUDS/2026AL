コードレビューとは

コードレビューとは、他の人が書いたコードを読んで改善点を見つける作業のこと。プロのソフトウェア開発では、ほぼ全てのコードがレビューを経てから本番環境に反映されます。

例題 1

バグのあるコードを見つける（正しさ）

Python
# --- バグのあるコード ---
def find_max_buggy(numbers):
    """リストの最大値を返す関数（バグあり）"""
    maximum = numbers[0]  # 空リストでエラー！
    for i in range(len(numbers)):
        if numbers[i] > maximum:
            maximum = numbers[i]
    return maximum

# --- 修正版 ---
def find_max_fixed(numbers):
    """リストの最大値を返す関数（修正版）"""
    if not numbers:  # 空リストチェックを追加
        print("警告: 空のリストです")
        return None
    maximum = numbers[0]
    for i in range(1, len(numbers)):  # 2番目から開始
        if numbers[i] > maximum:
            maximum = numbers[i]
    return maximum
  • バグ1: 空リストが渡されると numbers[0] で IndexError（インデックス・エラー）
  • 修正: if not numbers: で空チェックを追加（境界値チェック）
  • 改善: ループを range(1, ...) にして無駄な比較を削除

例題 2

可読性の改善

次の コードA と コードB は、まったく同じ計算（どちらも結果は 396.0）をします。違うのは名前の付け方とコメントだけです。まずは自分で読み比べてみましょう。

Python ─ コードA
def calc(x, y):
    z = x * y
    t = z * 0.1
    return z + t

print(calc(120, 3))  # → 396.0
Python ─ コードB
def total_price(unit_price, quantity):
    subtotal = unit_price * quantity
    tax = subtotal * 0.1
    return subtotal + tax

print(total_price(120, 3))  # → 396.0

❓ どちらが読みやすい？

コードA と コードB のうち、「何をしているコードか」が分かりやすいのはどちらでしょう？ A か B かを選び、その理由も考えてみましょう。（2つは同じ計算をします）

答えと解説を見る（同じ処理・違う名前 ─ 読みやすさはこう変わる）

読みやすいのは コードB。処理はコードAと全く同じでも、total_price（税込み合計）・unit_price（単価）・quantity（数量）のように意味のある名前とコメントがあるだけで、「単価×数量の税込み計算」だと一目で分かります。

コードA（読みにくい）コードB（読みやすい）理由
calc(x, y)total_price(unit_price, quantity)関数名・引数名で「何の計算か」が分かる
zsubtotal（小計）途中の値が何を表すか分かる
ttax（税）1文字では意味が伝わらない
コメントなし各行に短いコメント後で読む人（未来の自分）のため
例題 3

効率性の改善（リスト vs セット）

次の2つの関数は、どちらもリストの中に重複があるかを調べます（結果は同じ）。違うのは seen に list を使うか set を使うかだけ。データが大きくなると、どちらが速いでしょう？

Python ── AL14-ex3.py（実行して時間を測る）
import time

def has_duplicate_slow(data):  # seen に list を使う
    seen = []
    for item in data:
        if item in seen:
            return True
        seen.append(item)
    return False

def has_duplicate_fast(data):  # seen に set を使う
    seen = set()
    for item in data:
        if item in seen:
            return True
        seen.add(item)
    return False

# 重複なしの大きなデータ（最悪ケース = 最後まで全部調べる）
data = list(range(10000))

start = time.time()
has_duplicate_slow(data)
print("list 版:", time.time() - start, "秒")

start = time.time()
has_duplicate_fast(data)
print("set  版:", time.time() - start, "秒")

❓ どちらが速い？予想してから実行しよう

実行する前に予想しよう。list 版と set 版、どちらが速い？ 何倍くらい差がつく？ 予想できたら実行して、実際の秒数を確かめよう。

Notionに記録: ① どちらが速いかの予想と理由、② 実際の list 版・set 版それぞれの秒数、③ 速度差（何倍か）。
答えと解説を見る（list の探索 O(n) vs set の探索 O(1)）

速いのは set 版。理由は item in seen の速さの違い: list の in は先頭から順に全部照合するので要素数に比例（O(n)）、set の in はハッシュで一発（O(1)）。データが増えるほど差が開きます。

速度差の実例

データ数リスト版セット版速度差
1,0000.0123秒0.000089秒138倍
5,0000.3012秒0.000411秒733倍
10,0001.2048秒0.000823秒1,464倍

データ構造の選択だけで1000倍以上の速度差が生まれる！

例題 4

拡張性の改善（マジックナンバー → 定数）

コードの中に突然出てくる意味の分からない数字をマジックナンバーと呼びます。これを名前付きの定数にまとめると、あとで値を変えるのが1か所で済み、変更に強い（＝拡張しやすい）コードになります。

Python ─ 改善前（数字 1.1 が散らばる）
def price_with_tax(price):
    return price * 1.1          # 1.1 って何？

def total(prices):
    result = 0
    for p in prices:
        result += p * 1.1       # ここにも 1.1！
    return result
Python ─ 改善後（税率を定数にまとめる）
TAX_RATE = 0.1                  # 消費税率（変更はここ1か所だけ）

def price_with_tax(price):
    return price * (1 + TAX_RATE)

def total(prices):
    result = 0
    for p in prices:
        result += p * (1 + TAX_RATE)
    return result

❓ 消費税が 10% → 15% に変わったら？

改善前と改善後、それぞれ何か所直す必要があるでしょう？ 考えてみよう。

答えを見る

改善前は 1.1 を2か所（本物のプログラムでは何十か所にもなる）すべて 1.15 に直す必要があり、1つでも直し忘れるとバグになる。改善後は TAX_RATE = 0.1 を 0.15 に1か所直すだけで全体に反映される。これが「拡張性（変更に強いか）」の改善。

標準課題

バグを発見して修正する

次の stats 関数は、点数リストの合計・平均・最高点を返すつもりで書かれています。しかし stats([70, 85, 90, 60]) を実行すると (60, 15.0, 90) というおかしな結果になります（正しくは 合計305・平均76.25・最高点90）。このコードには複数のバグが潜んでいます。すべて見つけて修正しなさい。

Python ── AL14-std.py
def stats(scores):
    """点数リストの合計・平均・最高点を返す"""
    total = 0
    highest = 0
    for i in range(1, len(scores)):
        total = scores[i]
        if scores[i] > highest:
            highest = scores[i]
    average = total / len(scores)
    return total, average, highest

print(stats([70, 85, 90, 60]))
Notionに記録: 以下の内容を自分のNotionノートに記録してください。

記録する内容

  • 見つけたバグを全部（何行目が、どう間違っているか。バグは1つではありません）
  • それぞれなぜ間違った結果になるのか（原因の説明）
  • 修正版のコード全体を貼り付け、[70, 85, 90, 60] で正しい結果（合計305・平均76.25・最高点90）になることを確認
  • 境界値: 空リスト [] を渡すとどうなる？ どう対処すべきか

例題 例題1 解説

バグ版 find_max_buggy([]) を実行すると、numbers[0] の時点でリストが空のため IndexError が発生する:

Traceback (most recent call last):
  File "AL14-ex1.py", line X, in <module>
    print(find_max_buggy([]))
  File "AL14-ex1.py", line Y, in find_max_buggy
    maximum = numbers[0]
IndexError: list index out of range

一方、修正版 find_max_fixed([]) は if not numbers: で空チェックを行うため、エラーを出さずに警告メッセージを表示して None を返す:

警告: 空のリストです
None

この差が「正しさ」の改善ポイント。境界値（空リスト・0要素・負数など）を想定して事前チェックを入れることで、プログラムは予期せぬクラッシュを避けられる。find_max_fixed([5]) など要素1つのケースでも動作することを併せて確認しておくと安心。

例題 例題2 解説

改善前と改善後で計算結果は同じ（どちらも 396.0）。違うのは「読みやすさ」だけ:

改善前（何の計算か分からない）:
  def calc(x, y):
      z = x * y
      t = z * 0.1
      return z + t

改善後（買い物の税込み計算だと分かる）:
  def total_price(unit_price, quantity):
      subtotal = unit_price * quantity   # 小計
      tax = subtotal * 0.1               # 消費税
      return subtotal + tax              # 税込み合計

1文字変数（x, y, z, t）は書くときは速いが、1週間後の自分や他人がコードを読むときに「これは何だっけ？」と止まる原因になる。unit_price（単価）, quantity（数量）, subtotal（小計）, tax（税）のように役割が分かる英単語を使い、各行に短いコメントを添えると、処理の流れが一目で追えるようになる。これが「可読性」の改善。

例題 例題3 解説

data = list(range(10000))（重複なし＝全件探索が最悪ケース）で実行した結果例:

list 版 has_duplicate_slow: 約 0.21 秒
set  版 has_duplicate_fast: 約 0.0002 秒
速度差: 約 1000 倍

環境によって絶対値は変わるが、速度比は数百〜千倍のオーダーになる。理由は計算量の違い: リスト版は item in seen が O(n) なので全体で O(n²)、セット版はハッシュにより O(1) なので全体で O(n)。同じロジックでもデータ構造の選択だけでこれだけの差が出るのが「効率性」の改善ポイント。データが10倍になればリスト版は100倍遅くなり、セット版は10倍にしかならない。
