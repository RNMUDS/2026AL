説明

1.1 ハッシュテーブルとは

ハッシュテーブルは配列（スロット）とハッシュ関数の組み合わせです。

概念
キー "apple"  → ハッシュ関数 → インデックス 0 → テーブル[0] に格納
キー "banana" → ハッシュ関数 → インデックス 9 → テーブル[9] に格納
  • キーからハッシュ関数でインデックスを計算し、そのインデックスにデータを格納する
  • 検索・格納が平均 O(1)（データが何個あってもほぼ一定の速さ）で行える高速なデータ構造 → 下の補足で詳しく説明

補足: 「平均 O(1)」ってどういう意味？

O(1) は「オー・いち」と読み、データが何個あっても処理時間がほぼ一定であることを表す記号です（定数時間 / constant time）。O記法（オーダー記法）は「データの個数 n が増えたとき、処理時間がどんな割合で増えるか」をざっくり表す書き方です。

靴箱（げた箱）を思い出してください。「出席番号5番の人は5番の箱」とルールが決まっていれば、端から順に全部開けなくても 一発で自分の箱に手が届きます。これが O(1)。クラスが10人でも1000人でも、自分の箱を開ける手間は変わりません。

ハッシュ法も同じで、キーをハッシュ関数に入れれば「何番の箱に入れる／探すか」が即座に計算でき、配列の table[index] に一発でアクセスできます（端から順に調べる線形探索 O(n) とは対照的）。

データ数 nO(1)（ハッシュ法・理想）O(n)（線形探索）
100 件約 1 回の確認約 100 回の確認
1,000,000 件約 1 回の確認約 1,000,000 回の確認

なぜ「平均」が付くのか？ 衝突（→ 1.2）が起きると、線形探索法では隣のスロットを何回か確認してから目的のデータに届きます。つまり探すキーによって「確認した回数」が変わるのです。「いつでもちょうど1回」ではありません。

例: テーブルサイズ7に 1, 8, 3, 15 を線形探索法で入れた（1→[1] / 8→[2] / 3→[3] / 15→[4]）あと、それぞれを検索すると…

検索するキーたどるスロット確認した回数
1[1] で発見1 回
3[3] で発見1 回
8[1]→[2] で発見2 回
15[1]→[2]→[3]→[4] で発見4 回

回数は 1回・1回・2回・4回とバラバラ。これをならす（平均する）と (1+1+2+4) ÷ 4 = 2 回。1回のときもあれば4回のときもあるが、たくさん検索すれば「だいたい2回くらい」に落ち着く ── これが「平均」の意味です。

そして大事なのは、この平均回数（ここでは約2回）が データ数 n が100件でも100万件でも、ほとんど増えないこと（テーブルが混みすぎない限り）。だから「平均すれば、n によらずほぼ一定回数」＝ 平均 O(1) と呼びます。

※ ただしテーブルに詰め込みすぎる（負荷率が高い）と衝突が連鎖して平均回数が増え、最悪のケースでは O(n) まで悪化します。負荷率と性能の関係は発展課題で実験します。

1.2 衝突（Collision / コリジョン）とは

異なるキーが同じインデックスに格納されようとすること。「衝突」とは英語の collision (コリジョン = ぶつかること) の訳語です。

  • テーブルサイズは有限（例: 10 スロット）
  • 格納するキーは無限に存在しうる
  • 鳩の巣原理（pigeonhole principle）: 11羽の鳩を10個の巣箱に入れたら、必ずどこかの巣箱に2羽以上入る
100種類の苗字を10個の郵便受けに振り分けるなら、必ずどこかの郵便受けに複数の苗字が割り当てられます。これがハッシュテーブルで起きる「衝突」です。

コンピュータの中では、なぜ衝突が起きるの？

原因は、ハッシュ関数の最後にある % size（size で割った余り）という計算です。余りは必ず 0 〜 size−1 の範囲に収まるので、どんなキーを入れても、行き先は決まった個数のスロットのどれかになります。キーは無数に作れるのに行き先は有限個 ── だから別々のキーが同じ番号に当たることが必ず起こります。

具体例1: 数字を % 7 したとき（スロット7個）

余りは 0〜6 の7種類しかない
 7 % 7 = 0
14 % 7 = 0   ← 7, 14, 21, 28 … はぜんぶ [0] に行きたがる！
21 % 7 = 0
28 % 7 = 0
 3 % 7 = 3
10 % 7 = 3   ← 3 と 10 も同じ [3] でぶつかる

余りは 0,1,2,3,4,5,6 の7種類だけ。だから8個目以降の数字は、必ずどれかと余りが一致します。これが衝突です。（この 7,14,21,28,35 は標準課題1でそのまま出てきます。）

具体例2: 文字列のハッシュ関数（文字コードの和）

この授業のハッシュ関数は「文字コードの総和 ÷ size の余り」です。総和は文字を並べ替えても変わらないので、"apple" と "pleap"（同じ文字の並べ替え＝アナグラム）は必ず同じハッシュ値になり、衝突します（→ 例題3で確認します）。

つまり衝突は「ハッシュ関数の出来が悪いから」だけでなく、「無限の入力を有限のスロットに押し込む」以上、原理的に避けられないのです（→ だから次の 1.3 衝突解決法 が必要になります）。

1.3 衝突が起きたらどうする？（衝突解決法）

前の節で見たとおり、鳩の巣原理により衝突は原理的に避けられません。「衝突したらエラーにして諦める」のでは使いものにならないので、衝突が起きても正しく格納・検索できる工夫が必要です。この工夫を 衝突解決法（しょうとつかいけつほう / collision resolution） と呼びます。

衝突解決法には、大きく2つの流派があります。

流派考え方この回で学ぶ代表例
① オープンアドレス法
open addressing		衝突したら、テーブルの中の別の空きスロットを探して、そこに入れる。データはすべてテーブル（配列）の中に収まる。線形探索法（→ 1.4）
② チェイン法
chaining		各スロットにリストをぶら下げ、同じインデックスに来たデータをそのリストに追加していく。1つのスロットに何個でも入る。チェイン法（→ 1.5）
①オープンアドレス法は駐車場のイメージ。停めたい区画が埋まっていたら、空いている別の区画に停めます（→ 1.4）。②チェイン法は1つの郵便受けに郵便物を積み重ねるイメージ。同じ番号に来たものは、他の場所を借りずにその場所へまとめてためていきます（→ 1.5）。

次の 1.4・1.5 で、この2つを順番にくわしく見ていきます。

よくある疑問 Q&A（用語の整理）

ここまでで似た言葉がいくつか出てきました。先に整理しておきましょう。

Q1. 「衝突解決法」と「オープンアドレス法」は同じもの？

A. 衝突解決法は「衝突が起きたときの対処法」の総称。その中に オープンアドレス法（テーブル内で別のスロットを探す）と チェイン法（リストを連結する）の2つの大きな流派があります。線形探索法はオープンアドレス法の最も基本的な方式です。

Q2. 線形探索法（Linear Probing）と「線形探索（Linear Search）」は別物？

A. 別物です。線形探索（第3回）は配列を端から順に調べる探索アルゴリズム。線形探索法 / 線形プロービングはハッシュテーブルで衝突したときに「+1ずつスロットをずらして空きを探す」方法。日本語では似た名前ですが、英語では Linear Search と Linear Probing で区別されます。

Q3. 「チェイン法」の「チェイン」って何？

A. Chain = 鎖（くさり）。各スロットから連結リストが「鎖のように」伸びる様子を表しています。「鎖法」とも訳されます。

1.4 線形探索法（Linear Probing / リニアプロービング）

Probing（プロービング）は「探りを入れる」という意味。Linear（リニア）は「直線的に・一直線に」。つまり「1つずつ直線的に空きを探す」方法。オープンアドレス法の一種です。

駐車場を想像してください。目的の番号の駐車場が埋まっていたら、隣の空いている場所に停めます。探すときも同じルートで探します。

衝突が起きたら次のスロットを試す。それも埋まっていたらさらに次へ。具体的には index = (index + 1) % size で次の位置を計算します。

1.5 チェイン法（Chaining / チェイニング）

何をする方法？　線形探索法（1.4）は「衝突したら別のスロットへ逃がす」方法でした。チェイン法はその逆で、衝突したデータを動かさず、同じスロットにまとめて置いておく方法です。そのために、各スロットには1個分のデータではなく リスト（連結リスト）＝「いくつでも入る箱」 を持たせます。「鎖法」「連結リスト法」「セパレートチェイニング（separate chaining）」とも呼ばれます。

マンションの郵便受けを想像してください。1つの部屋番号に複数の住人がいても、郵便受けの中に郵便物を順番に積み重ねておけば全員分が入ります。衝突したデータを別の空きスロットへ移して分散させる線形探索法とは対照的に、チェイン法は同じ場所にためておくのが特徴です。

何のため？（目的）　衝突は鳩の巣原理で必ず起きます（→ 1.2）。線形探索法では衝突のたびに別の空きスロットを占領していくため、テーブルが埋まってくると無関係なキーの場所まで巻き込んで遅くなったり（クラスタリング）、空きが尽きるともう格納できなくなります。チェイン法は「衝突したものは同じ場所のリストに足すだけ」にすることで、この問題を避けるのが目的です。

メリット（線形探索法と比べて）

  • テーブルが満杯にならない: リストはいくらでも伸ばせるので、データ数がテーブルサイズを超えても格納できる（負荷率 > 1 でもOK）。
  • クラスタリングが起きにくい: 衝突しても他のスロットを占領しないため、無関係なキーを巻き込まない。
  • 削除が簡単: そのスロットのリストから取り除くだけ。線形探索法のような「削除済みマーカー（tombstone）」の工夫が要らない。

デメリット

  • リストをつなぐための追加メモリが必要。
  • 同じスロットにデータが集中すると、そのリストを端から順にたどることになり遅くなる（その部分は O(n) に近づく）。
概念
テーブル[3] → [("apple", 100), ("pleap", 999)]
テーブル[9] → [("banana", 80)]

2つの方法を、場面ごとに並べて比べてみましょう。

比べるポイント線形探索法
（オープンアドレス法）		チェイン法
衝突したとき
どうする？		 入れたい場所が埋まっていたら、隣へ1つずつずれて空いているスロットを探し、見つけた所に入れる。 場所は動かさず、そのスロットが持つリストの末尾に追加する。

例題 1

配列をテーブルとして使う

サイズ10の配列を作成し、ハッシュ関数でインデックスを計算してデータを格納します。

Python
table_size = 10
table = [None] * table_size  # 全スロットをNoneで初期化

def hash_function(key, size):
    total = 0
    for char in key:
        total = total + ord(char)
    return total % size

key = "apple"
value = 100
index = hash_function(key, table_size)
print(f"'{key}' のハッシュ値: {index}")

table[index] = (key, value)
print(f"テーブル[{index}] に ('{key}', {value}) を格納しました")

例題 4

線形探索法で格納と検索

Python
def insert_with_probing(table, key, value):
    size = len(table)
    index = hash_function(key, size)
    original_index = index
    probe_count = 0
    while table[index] is not None:
        if table[index][0] == key:
            break
        probe_count = probe_count + 1
        next_index = (index + 1) % size
        index = next_index
        if index == original_index:
            print("テーブルが満杯です")
            return -1
    table[index] = (key, value)
    print(f"  insert '{key}': 初期={original_index}, 探索{probe_count}回 → [{index}]")

def search_with_probing(table, key):
    size = len(table)
    index = hash_function(key, size)
    start_index = index
    probe_count = 0
    while table[index] is not None:
        probe_count = probe_count + 1
        if table[index][0] == key:
            print(f"  search '{key}': [{index}]で発見, 探索{probe_count}回")
            return table[index][1]
        next_index = (index + 1) % size
        index = next_index
        if index == start_index:
            break
    print(f"  search '{key}': 見つかりません")
    return None

table = [None] * 10
insert_with_probing(table, "apple", 100)
insert_with_probing(table, "pleap", 999)  # appleと衝突
search_with_probing(table, "apple")
search_with_probing(table, "pleap")

例題 5

HashTable クラスの作成

insert / search / delete / display メソッドを持つクラスを作成します。

Python
class HashTable:
    def __init__(self, size=10):
        self.size = size
        self.table = [None] * size
        self.count = 0

    def _hash(self, key):
        total = 0
        for char in key:
            total = total + ord(char)
        return total % self.size

    def insert(self, key, value):
        index = self._hash(key)
        original = index
        while self.table[index] is not None:
            if self.table[index][0] == key:
                break
            next_index = (index + 1) % self.size
            index = next_index
            if index == original:
                return -1
        self.table[index] = (key, value)
        self.count = self.count + 1

    def search(self, key):
        index = self._hash(key)
        start = index
        while self.table[index] is not None:
            if self.table[index][0] == key:
                return self.table[index][1]
            next_index = (index + 1) % self.size
            index = next_index
            if index == start:
                break
        return None

    def delete(self, key):
        index = self._hash(key)
        start = index
        while self.table[index] is not None:
            if self.table[index][0] == key:
                self.table[index] = None
                self.count = self.count - 1
                return True
            next_index = (index + 1) % self.size
            index = next_index
            if index == start:
                break
        return False

# --- テスト ---

ht.insert("banana", 80)
print(ht.search("apple"))   # → 100
ht.delete("apple")
print(ht.search("apple"))   # → None

# 標準課題1で作ったテーブル（key%7で格納、線形探索法）
table = [14, 21, 7, 28, 35, None, None]

def search(table, key):
    h = key % SIZE
    count = 0
    while table[h] is not None:
        count = count + 1
        print(f"  比較{count}: table[{h}]={table[h]}")
        if table[h] == key:
            return h, count
        next_h = (h + 1) % SIZE
        h = next_h
    return -1, count

for key in [28, 35, 10]:
    print(f"検索: key={key}")
    pos, c = search(table, key)
    print(f"  結果: pos={pos}, 比較回数={c}")

例題 例題1 やってみよう 解答

key = "banana" に変更して hash_function(key, 10) を実行した結果:

ord('b')+ord('a')+ord('n')+ord('a')+ord('n')+ord('a')
= 98 + 97 + 110 + 97 + 110 + 97 = 609
609 % 10 = 9

'banana' のハッシュ値: 9
テーブル[9] に ('banana', 80) を格納しました

ハッシュ関数は「文字コードの総和を size で割った余り」を返すだけ。"apple"（→0）と "banana"（→9）のように、入力が少し変わるとインデックスは大きく散らばる。これがハッシュ法の O(1) で格納先が決まる という性質の本質。

例題 例題2 やってみよう 解答

末尾に print(table) を追加して実行した結果:

  'apple'  → インデックス 0 → 格納完了
  'banana' → インデックス 9 → 格納完了
  'cherry' → インデックス 3 → 格納完了
  'date'   → インデックス 4 → 格納完了

[('apple', 100), None, None, ('cherry', 150), ('date', 200),
 None, None, None, None, ('banana', 80)]

None のスロット数: 6個（インデックス 1, 2, 5, 6, 7, 8）

4件のデータをサイズ10のテーブルに入れたので、負荷率 = 4/10 = 0.4。空きスロットが6個あり、まだ衝突は起きていない。負荷率が低いうちはハッシュ法の性能が最大限に発揮される（理想的な O(1)）。

例題 例題3 やってみよう 解答

5つのキーのハッシュ値を計算した結果:

=== 各キーのハッシュ値 ===
  'apple'  → インデックス 0
  'pleap'  → インデックス 0   ← apple と衝突
  'banana' → インデックス 9
  'ananab' → インデックス 9   ← banana と衝突
  'cherry' → インデックス 3

衝突しているペア:
  (apple, pleap)   → どちらもインデックス 0
  (banana, ananab) → どちらもインデックス 9

"apple" と "pleap"、"banana" と "ananab" はそれぞれ 同じ文字を並び替えただけ（アナグラム）。文字コードの総和は順序に依存しないため、必ず同じハッシュ値になる。これは「総和型ハッシュ関数の弱点」で、実用ではより複雑なハッシュ関数（例: 文字位置で重み付け）を使う必要がある。

例題 例題4 やってみよう 解答

線形探索法で "apple" と "pleap" を挿入・検索した結果:

  insert 'apple': 初期=0, 探索0回 → [0]
  insert 'pleap': 初期=0, 探索1回 → [1]   ← 衝突して1つズレた
  search 'apple': [0]で発見, 探索1回
  search 'pleap': [1]で発見, 探索2回   ← apple を見てから pleap へ

apple の検索回数 = 1回
pleap の検索回数 = 2回（apple のスロットを経由するため +1）

"pleap" は本来インデックス0に行きたいが、すでに "apple" が居るので 右隣の1番に「ずらされて」格納される（線形探索法 / オープンアドレス法）。検索時も同じ経路をたどるため、衝突した側は 探索回数が +1 される。衝突が増えるほど検索性能は劣化する。

例題 例題5 やってみよう 解答

ht.delete("apple") の後に ht.insert("grape", 200) と ht.search("grape") を追加した結果:

ht.insert("apple", 100)   → table[0] = ('apple', 100)
ht.insert("banana", 80)   → table[9] = ('banana', 80)
ht.search("apple")        → 100
ht.delete("apple")        → table[0] = None  （空きに戻る）
ht.insert("grape", 200)   → 'grape' のハッシュ = (103+114+97+112+101) % 10
                          = 527 % 10 = 7 → table[7] = ('grape', 200)
ht.search("grape")        → 200

削除された apple のスロット（インデックス0）は None に戻り、再利用可能。

"grape" はハッシュ値が 7 なので、空きスロット table[0] ではなく table[7] に格納される。削除したスロットは別キーで再利用されるわけではない。なお、本実装は delete でスロットを None に戻すシンプル版だが、線形探索法では本来「削除済みマーカー（tombstone）」を置かないと、衝突連鎖の途中で検索が打ち切られて見つからなくなるバグが起こりうる点に注意。
